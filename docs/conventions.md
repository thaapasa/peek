# Coding Conventions

## Writing (docs + comments)

Terse. Not CLAUDE.md-caveman, but far tighter than prose default. Give the beef, cut the
boilerplate around it. Assume a sharp reader who wants the point, not 10 sentences of setup.

- **Lead with the fact.** What + *why* in the first clause. No throat-clearing ("This module is
  responsible for…" → "Parses X.").
- **One idea, one line.** Drop filler, hedging, restated context. Fragments fine.
- **Comment the non-obvious** — invariants, gotchas, *why* this not that. Don't narrate what the
  code plainly says.
- **Fix verbosity in passing.** Editing a doc / `//!` header / comment? Tighten the bloat you touch.
- **Write new docs terse from the start.**

## Errors

- `anyhow::Result` for app errors; `thiserror` for library-style typed errors.
- No `unwrap()` outside tests. Propagate with `?`.

## CLI

- All args on one clap-derive `Args` struct in `cli.rs`.
- TTY stdout → interactive viewer. Pipe → direct output.

## Color

- All colored output via `PeekTheme::paint()`. Never hand-write ANSI (`\x1b[...m`) — `StyleMode`
  picks the wire form (24-bit / 256 / 16 / grayscale / plain) in one place.
- Semantic roles (`heading`, `label`, `value`, `accent`, `muted`, `warning`). Shades via
  `lerp_color()`. No hardcoded RGB.
- Target truecolor; degrade gracefully.
- **Sanitise file-controlled text before painting it.** Any string sourced from file bytes (content
  lines, metadata, entry/file names, rendered prose) must pass through
  `peek_io::sanitize_terminal_controls` *before* peek wraps it in its own SGR — otherwise raw
  ESC/OSC in the file reaches the terminal (clipboard writes, title spoofing, hyperlink injection).
  There is no single global choke: peek's own escapes and content escapes are indistinguishable once
  mixed, so sanitise at each producer's input (e.g. line decode, the InfoValue text path,
  `emit_styled`, each listing `flat_line`). A new renderer that paints file text must do the same.

## Themes

- `.tmTheme` files in `themes/`, embedded via `include_str!()`.
- `PeekTheme` roles derive from syntect theme settings.
- Add a theme: drop the `.tmTheme`, add a `PeekThemeName` variant, wire `include_str!` / `cli_name`
  / `tmtheme_source` / `next` / `help_text`.

## Modes

One abstraction, two output paths.

- **`Mode` trait** (`viewer/modes/mod.rs`) — the single rendering contract. Each file type composes
  a `Vec<Box<dyn Mode>>` via `Registry::compose_modes`; see
  [architecture.md](architecture.md#key-abstractions) for the mode table + trait shape.
- **Interactive** (`viewer_session::interactive::run`, in the bin) — event loop calls
  `Mode::render_window(ctx, scroll, rows) -> Result<Window>` per redraw. Streaming modes honour the
  window; fixed-content modes (Info/Help/About) materialise + slice via `slice_window`.
- **Pipe** (`main`) — first non-aux mode (first, for binary), `Mode::render_to_pipe(ctx, &mut
  PrintOutput)`. Default impl renders full viewport + writes each line; override when streaming or
  byte-faithful output matters (HexMode streams chunks; ContentMode preserves trailing-newline).

Adding a file type: add a `Mode` impl (or reuse `ContentMode`) + a line in `compose_modes`. Modes
that re-render on resize override `rerender_on_resize`; modes owning scroll (Hex's byte offset)
override `owns_scroll` + `scroll`.

## File types

Each type is a self-contained dir at `crates/peek-types/src/types/<name>/` owning the reader side —
input read, info gather, info render, view mode(s). **Detection** (format enum + extension/MIME/
content-sniff) lives in `peek-detect` at `crates/peek-detect/src/types/<name>.rs`, *not* the reader
— keeps detection independent of reader/viewer (Cargo-enforced). The reader re-exports its format
enum at module root (`mod.rs`: `pub use peek_detect::types::<name>::<Name>Format;`). Code outside
`types/<name>/` only **wires** the type in.

Owned by the type module:

- `mod.rs` — module decls + brief overview. No logic.
- `info_gather.rs` — `gather_extras(...)` returns metadata as `Extras` (`Box<dyn InfoExtras>`) via
  `Box::new(<Stats>)`. Single entry called from `info::gather` dispatch. (Tiny types: combine
  gather + render in one `info.rs`.)
- `info_render.rs` — the info section, both outputs: themed terminal (`render_section`) + `--info
  --json` (`json_section`). Normally one `#[derive(serde::Serialize, InfoView)]` view struct drives
  both — when the view projects from a separate stats struct via `From<&Stats>`, the
  `render_section` / `json_section` pair is generated by the `info_section!` macro, not hand-written;
  irregular sections use `InfoRow` or hand-impl (see architecture.md → "Adding a new file type" for
  the three modes). Bound to `InfoExtras` by one `impl_info_extras!` row in
  `info_impls.rs`; `info::render` dispatches dynamically — no per-type render match.
- `reader.rs` / `backends/` (optional) — format parsing, streaming where possible (CLAUDE.md
  "Stream, don't load").
- `mode.rs` / `animation_mode.rs` (optional) — `Mode` impl(s), wired into `compose_modes`.

Wired in (centralized — never duplicated inside `types/<name>/`):

- `crates/peek-detect/src/detect.rs` — `FileType::<Variant>` + orchestrator wiring;
  `crates/peek-detect/src/types/<name>.rs` — format enum + sniff helpers.
- `src/gather/mod.rs` — dispatches `FileType` → `types::<name>::info_gather::gather_extras`.
- `crates/peek-types/src/types/info_impls.rs` — one `impl_info_extras!(<Stats>,
  ...::render_section)` binding the stats struct to `InfoExtras`. `info::render` dispatches
  dynamically.
- `src/compose.rs` (`Registry::compose_modes`) — dispatches `FileType` → mode stack.
- `src/extract/extract.rs` (container types only) — dispatches `FileType` →
  `types::<name>::extract::extract`.

Adding a type: create the dir, add the wiring above (detection, gather arm, one `info_impls.rs`
row), fill in gather + render. Mode optional (text-like reuse `ContentMode`).

Anti-pattern: a `match file_type` inside `types/<name>/` or anywhere but the wiring sites. Branch on
file type only at a wiring site; the per-arm body lives in the type module.

## Crate imports

Name dependency crates directly — `peek_io::`, `peek_detect::`, `peek_theme::`,
`peek_foundation::{viewer, info, …}`. No in-crate re-export façade or `use peek_x as y` alias to
dodge the crate name. The path should say which crate an item comes from and agree with `Cargo.toml`.
A re-export of a stable leaf buys nothing — one more jump-to-def hop, a path hiding the real source.

Re-export from a dependency **only** when the bare path genuinely can't carry, reason stated at the
re-export site:

- **Dependency type is part of this crate's public API.** `peek-detect` re-exports
  `peek_io::compression::CompressionFormat` because public `FileType::Compressed(..)` embeds it. The
  per-type format-enum re-export (`pub use peek_detect::types::<name>::<Name>Format`) is the same:
  the reader surfaces the enum it's built around as its own root API.
- **Proc-macro surface.** `info::InfoView` re-exports the derive from `peek-foundation-derive` —
  proc-macro crates export only macros.
- **Macro hygiene.** `peek-foundation` keeps `pub use peek_theme as theme` solely so the
  `#[derive(InfoView)]` expansion's `::peek_foundation::theme::PeekTheme` path resolves through the
  one crate every deriving crate depends on. Not for hand-written use.

## Module organization

- **Split before unwieldy.** A file past ~400 lines mixing unrelated concerns is a refactor signal.
  Examples: `info::gather`, `types/image` both split from fat `mod.rs` files; `viewer/ui/screen.rs`
  lifted out of `state.rs` once the frame-buffer cache became a third concern beside mode-stack
  management + key dispatch.
- **`mod.rs` stays small** — module decls, re-exports, small glue types. Topic logic lives in its
  own concern-named file (`exif.rs`, `xmp.rs`, `animation_mode.rs`, `mode.rs`, `screen.rs`).
- **Colocate by concern, not by trait.** All SVG rasterization in `types/image/pipeline/svg.rs` —
  "how does SVG work" finds one file. Grouping by abstraction shape scatters topic knowledge.
- **Mechanism doesn't leak across concerns.** When one type's fields exist only to serve a separate
  concern (a frame-cache `Vec<String>` on a mode-stack struct just so `draw` can diff it), the cache
  + its draw method belong in their own type with a narrow API. The original loses surface area.
- **Splitting earns its keep when it cuts what the reader holds in head.** Don't split a 200-line
  file doing one thing well. Split when one file demands multiple unrelated mental models.

## Arithmetic

Inline arithmetic fine for simple things — a sum, average, one `min`/`max` clamp, a 2–3 step ratio.
The moment a calc crosses into a multi-step shape (effective grid from base × zoom, viewport clamp +
max-scroll, cell→pixel projection, anchored zoom-around-centre, packed-bit decode, byte-offset →
line+column) it earns a named helper.

- **Name the calculation, not the formula.** `zoomed_view.pixel_roi(...)` beats
  `let crop_w = x1.saturating_sub(x0).max(1);` repeated three places.
- **Lift on the first duplicate, not the third.** Two parallel sites with the same formula is the
  threshold — by the third you've paid the drift cost. Especially when both sites *must* agree
  (pan-bounds reported by one must match the clamp the other applies); the compiler doesn't enforce
  parallel-arithmetic agreement, a shared helper does.
- **Pin formulas with tests in the helper module**, not each caller. Move inline tests over when
  extracting.
- **Free fn vs method**: method (`ZoomedView::pixel_roi`) when the calc reads several struct fields;
  free fn (`anchor_zoom_change`) when it operates on caller-supplied values.

Concretely: any block over ~5 lines, repeated across files, or using casts + `saturating_*` +
`.max(1)` to defend edge cases — extract it. That pattern signals math with invariants worth naming.

## Tests

- **New `info::gather` / `info::render` / `input::detect` functionality needs fixture-based tests.**
  Full `detect` → `gather` pipeline tests at `src/gather/tests.rs`; per-type parser tests in the
  owning `crates/peek-types/src/types/<name>/` module. Use real files in `test-images/` /
  `test-data/`. Fixtures sit at the **workspace root**, so the path depends on crate depth: the root
  bin uses `env!("CARGO_MANIFEST_DIR")`; member crates (peek-types / peek-foundation) are two levels
  deeper — use `concat!(env!("CARGO_MANIFEST_DIR"), "/../..")` (relative `include_bytes!` depth
  shifts the same way). Each test runs the pipeline + asserts known-true facts (dimensions, kind,
  indent style, root element). These layers are thin wrappers over external parsers (image, exif,
  quick-xml, serde_json) — fixture tests catch upstream regressions + pin extraction to ground truth.
- **Synthetic streaming-pass tests stay put** — UTF-8 chunk-boundary cases in `info::gather::text`
  assert easier against tiny synthetic inputs. Fixture tests complement, don't replace.
- **Add a fixture if you need one.** `test-data/` / `test-images/` are first-class; extending them
  is part of the task.

## Standards

- IANA-registered MIME types only (RFC 6648 — no `x-` prefixes). Languages without registered types
  fall back to `text/plain`.
